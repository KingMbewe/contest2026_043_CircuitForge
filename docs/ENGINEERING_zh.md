# VelaPaw —— 工程技术详解

关于 VelaPaw 如何构建的技术说明：端侧 AI 流水线、对 openVela 的深度使用、攻克的最难问题，以及性能工程。本文是 [README](../README_zh.md) 的配套材料，面向希望了解实现细节的读者。

---

## 一、系统总览

所有功能都运行在单颗 **ESP32-S3**（Xtensa LX7，8 MB PSRAM，16 MB 闪存）上，操作系统为 **openVela / NuttX**，界面基于 **LVGL** 触摸屏。没有配套手机、没有云端、也不依赖网络——采集、推理、排程、计时与投料全部在本地完成。

**闪存布局（16 MB）**

| 偏移 | 内容 | 大小 | 说明 |
|---|---|---|---|
| `0x000000` | 固件（`nuttx.bin`） | ~750 KB | openVela + 应用 + LVGL |
| `0x600000` | 身份识别模型（`velapaw.tflite`） | 1.44 MB | 开机时从闪存加载入 PSRAM |
| `0x760000` | 体况评估模型（`bcs.tflite`） | 626 KB | 开机时从闪存加载入 PSRAM |
| `0x800000` | 已登记宠物（magic `VPAW`） | 8 KB | 名称、时间表、面部嵌入向量 |
| `0x810000` | 宠物头像（magic `VICN`） | 32 KB | 卡片缩略图 |

两个神经网络**过大而无法内存映射**——在 1.4 MB 的 `const` 数组映射完成之前，DROM0 MMU 窗口就已耗尽——因此它们以原始数据块的形式烧入闪存，在开机时通过 NuttX 软件 `spi_flash_read` 路径读入 PSRAM 缓冲区。由于闪存读取会挂起 CPU 缓存，该读取运行在一个短生命周期的线程上，其栈是一块 `.bss`（内部 SRAM）缓冲区。

## 二、识别流水线

```
摄像头画面 ─► 嵌入向量（TFLM INT8，后台工作线程）─► 与已登记宠物做余弦匹配
                                                            │
                                                  宠物 id + 分数 + 间隔
                                                            │
                                         排程门控：这只宠物今天是否有某一餐
                                         已到时间且尚未进食？
                                                  │是            │否
                                            投喂 N 克         提示下一餐时间
                                                  │
                                       记入历史 · 趋势 · 体况评估
```

**开集，而非闭集。** 识别采用度量学习，而不是 N 分类器：模型把一帧 128×128 画面映射为经 L2 归一化的 128 维嵌入向量，登记时保存若干张照片的平均嵌入，匹配则是与已登记集合做余弦相似度比较。其实际收益是——**新增一只宠物无需重新训练**：登记是运行时操作，而"接受/拒绝"的判定是一个可调阈值。（有一点值得知道：对于通用特征提取器而言，拒绝任意的"非宠物"物体本身就很难，因此登记质量——贴近、光线良好的正脸照——是影响误识别的最主要因素。）

**推理不占用 UI 线程。** 约 1.3 秒的 `Invoke()` 运行在专门的工作线程上；LVGL 主循环把一帧交给它后继续渲染，因此推理期间触摸与摄像头预览保持流畅。识别还是**按需触发**的（当宠物出现在食盆前时才运行，而非持续运行），以此约束计算量。

## 三、对 openVela 的深度使用

VelaPaw 不是叠在 BSP 之上的一层薄应用——它在整个技术栈上都对 openVela 做了充分运用：

- **`apps/mlearning/tflite-micro`** 是 AI 运行时。应用直接链接它（`backend_tflm.cc`），并运行两个独立的 `MicroInterpreter`（身份识别 + 体况评估），张量内存池位于 PSRAM。
- **LVGL**（openVela 图形栈）驱动四标签页的触摸界面。
- **自定义板级驱动**（`board/esp32s3_st7789.c`）从零开始，基于 ESP32-S3 外设驱动：
  - **ST7796 显示屏**，走硬件 SPI2 + GDMA；
  - **OV5640 摄像头**，通过 **LCD_CAM** 外设配合一个 GDMA 接收通道（经 SCCB/I²C 配置）——通过 **30 cm 排线 + 转接板**引出，使摄像头可独立于主板安装（见 [`hardware/README.md`](../hardware/README.md)）；
  - **PCF85063 RTC**，走 I²C（直接寄存器访问——不启用 `CONFIG_RTC`，从而保住 USB-CDC 控制台）；
  - **28BYJ-48 步进电机投料**，经 **ULN2003** 驱动板用四个 GPIO 驱动（IN1–IN3/IN4 用 GPIO9/10/11/**43**——43 即 U0TXD，因控制台走 USB-Serial/JTAG 而空出可用；GPIO12/13/15 是 ES8311 编解码器独占的 I²S 总线，改用于语音设置时间表），由软件按相序步进。
- **开机自启**（`board/esp32s3_appinit.c`）从 `board_app_initialize()` 启动应用——NSH 在 `esp32s3_bringup()` 注册好 LCD/触摸/摄像头之后，通过 `boardctl(BOARDIOC_INIT)` 调用它——因此设备上电即进入 UI，同时仍保留了可用于调试的 shell。

## 四、最难的问题：硬件 SPI 显示

这是本项目中最具代表性的一段硬件调试经历。

**现象。** 在硬件 SPI 下，*全屏*写入能正常显示，但*任何局部窗口*写入（`CASET`/`RASET` 指向一个子矩形 + `RAMWR`）都不出现——而完全相同的字节序列走软件位翻转（bit-bang）的 GPIO 路径却完美工作。它经历了约 60 次软件与配置层面的编译改动（帧缓冲镜像、DMA 开关、软件 CS、PSRAM 一致性修复、强制引脚布线）仍无法解决。

**方法——测量，而非猜测。** 用逻辑分析仪（FX2 克隆 + sigrok/PulseView）时，SPI 引脚无法直接探测——它们未引出到排针——于是板级固件通过 GPIO 矩阵把 `FSPID_OUT`/`FSPICLK_OUT` **镜像**到空闲的排针 GPIO 上，再加一路触发标记。关键的第一步是一次**基准验证测试**：在探测引脚上驱动四路已知的方波，在它们读数干净之前拒绝相信任何采集结果。这一步立刻暴露出一个此前一直产生乱码的接线/接地问题——只有在此之后，真正的采集才变得可信。

**发现。** 解码后的采集显示 ESP32 发出的是**逐字节完全正确**的 `CASET 00 28 00 8B / RASET 00 28 00 8B / RAMWR / 像素` 序列——指令正确、DC 对齐正确、每字节恰好 8 个干净的时钟沿、零毛刺。外设自始至终是清白的。

**根因。** 屏的**片选被硬接为低电平**，因此它永远无法在 CS 沿上重新同步自己的位计数器——它会一直数时钟沿。固件先用位翻转做屏初始化，*之后*再把引脚交给 SPI 外设；这一引脚交接会让时钟多/少一个沿，从那一刻起屏就偏了一位。此后每条指令都被解码成乱码，`RAMWR` 永远不被识别，没有像素写入 GRAM，屏幕就一直显示位翻转最后画上去的内容——看起来就像"硬件 SPI 什么都没画出来"。

**修复。** 先把引脚交给 SPI 外设，**然后硬件复位屏**（软件复位行不通——它自身也会被误读），再完全走 SPI 做整套初始化。当屏在 SPI 控制下重新同步后，局部窗口即可正确渲染。

**收益。** 路径打通后，显示彻底摆脱了位翻转、改走硬件 SPI（见第五节）。一个看似死路的 bug，最终变成了一次性能提升。

## 五、性能工程

**在 LX7 上使用 ESP-NN（推理约 5 倍提速）。** 身份识别模型以深度可分离卷积为主，在 TFLite-Micro 的*参考*算子上运行很慢（约 6.75 秒/次）。为 Xtensa LX7 接入 **ESP-NN** SIMD 算子后，降到**约 1.3 秒**。棘手之处在于：ESP-NN 算子集要放进 tflite-micro 的 kernel 目录，并把对应的*参考*算子过滤掉以避免重复符号；另外，一类"首个 conv 就崩溃"的现象其实是**陈旧的增量编译**所致、而非算子 bug——干净编译后即稳定运行。

**硬件 SPI + DMA 显示（UI 重绘约 4 倍提速）。** SPI 路径修正后（第四节），显示从逐像素位翻转（CPU 翻转 GPIO）改为使用硬件 SPI2 外设、运行在 **40 MHz + GDMA**。一次 480×320 全屏重绘从**约 246 毫秒降到约 61 毫秒**。有两个细节很关键：像素行要经内部 SRAM 缓冲中转，因为 SPI DMA 无法缓存一致地读取 PSRAM；地址窗口设置也从 11 次 SPI 调用合并为 5 次（LVGL 每次 `putarea` 都会设置一次窗口）。

## 六、编译与可复现性说明

一些不那么显而易见的约束，记录于此以便复现编译：

- **应用与库的宏定义必须一致。** 应用与预编译的 `tflite-micro` 库共享头文件，因此对头文件可见的宏必须完全一致。尤其是 `TF_LITE_STATIC_MEMORY` 会改变 `TfLiteTensor` 的布局——只在一侧定义它，会让 `AllocateTensors` 通过、却让首个 `Invoke` 通过错位指针写入并卡死整颗 SoC。Makefile 精确对齐了库的宏集合。
- **`-fno-threadsafe-statics`** 是 C++ 编译标志中必需的：没有它，TFLM 初始化中第一个函数局部静态变量会在本 libsupc++ 构建上于 `__cxa_guard_acquire` 处死锁（是静默挂起，而非崩溃）。
- **配置改动会重新克隆 esp-hal**，从而回退一处自旋锁初始化补丁；任何 defconfig 改动后的首次编译可能需要重新打上该补丁。

### ESP-NN 加速——属于公共仓库改动，以 fork/PR 提供

约 1.3 秒的推理数据依赖 **ESP-NN** SIMD 算子，而该集成会改动一个**公共** openVela 仓库（`apps/mlearning/tflite-micro`）。按大赛规则——*公共仓库的改动应以 fork + PR 提交到 `dev-ai-contest-2026` 分支，而非提交进本队仓库*——因此 ESP-NN 的工作以 fork/PR 形式交付，而不在本仓内 vendored。**开箱即用时，本队仓库使用参考算子即可编译并运行（约 6.75 秒）；应用 ESP-NN fork 后降至约 1.3 秒。**

该集成由三部分组成：

1. **esp-nn 库**（Espressif 的 Apache-2.0 许可、面向 Xtensa LX7 的 SIMD 算子），置于 `apps/mlearning/esp-nn/`。
2. **算子包装层**（`conv`、`depthwise_conv`、`fully_connected`、`pooling`、`add`、`mul`、`softmax`），放入 `apps/mlearning/tflite-micro/tflite-micro/tensorflow/lite/micro/kernels/esp_nn/`。
3. **一段 Makefile 逻辑**，位于 `apps/mlearning/tflite-micro/Makefile`，用 `-DESP_NN=1 -DCONFIG_NN_OPTIMIZED -mlongcalls` 编译 esp-nn 源码、加入其头文件目录，并**过滤掉对应的参考算子**以避免重复符号。

具体的算子包装文件、Makefile 逻辑块，以及逐步复现步骤，作为参考材料提供于 [`docs/esp-nn/`](esp-nn/)。

> **PR：** _`<fork/PR 链接——开 PR 后填写>`_

集成中遇到的两个坑：esp-nn 的汇编源文件（`*esp32s3.c`）被排除（采用 opt-C 路径）；早期"首个 conv 崩溃"经排查是**陈旧的增量编译**所致、而非算子问题——干净重编即稳定运行。

## 七、设备外：模型训练

两个 INT8 模型均在设备外用 [`host/`](../host/) 中的流水线（TensorFlow/Keras）训练。身份识别模型是一个 MobileNetV3-Small 主干，配合空间注意力 **TSFM** 模块和一个 ArcFace 度量学习头；经 INT8 训练后量化导出为 `.tflite`，其算子全部为 TFLM 内置算子。体况评估模型是同样方式训练的一个紧凑三分类 CNN。fast 与 accurate 两个模型的对比见 [`docs/BENCHMARK_AB.md`](BENCHMARK_AB.md)。
